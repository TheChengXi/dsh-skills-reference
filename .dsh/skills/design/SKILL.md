# 结构设计

以下规则具有最高优先级。

## 核心规则

跨层依赖是 bug。结构设计阶段强制排除，不允许进入编码阶段。

依赖方向只有一种：上层可依赖下层，下层绝不能依赖上层，不允许跨层依赖。

如果项目已有自己的分层模式，跟随它的命名。

---

## 工作流程

### 1. 判断项目状态

- **新项目**（代码从无到有）→ 从零设计结构
- **已有项目**（有既有代码）→ 顺应原有结构，只做增量
- **拍板不了** → 联网搜索

### 2. 执行

#### 2a. 新项目 — 从零设计

分析需求中的核心功能，做模块划分：

- **上层**：处理用户交互、外部输入输出
- **中间层**：业务逻辑编排
- **下层**：数据存取、外部服务

依赖方向：上层 → 中间层 → 下层。下层绝不能反向依赖。

模块划分原则：每个模块只做一件事。
接口原则：只暴露必要的，隐藏实现细节。

完成后输出模块清单和依赖链。

#### 2b. 已有项目 — 顺应原有结构

1. **读原有结构**：先看项目现有的分层模式，无论叫什么名字，跟随它
2. **找落脚点**：新功能放在哪一层哪个模块
3. **验依赖**：新增依赖必须不跨层。原有结构中存在跨层依赖 → 在 design.md 中标明，作为本次一并修复项
4. **输出改动**：改动点清单 + 新增文件清单

#### 2c. 拍板不了 — 联网搜索

根据项目类型定向搜索：
- **前端项目** → 搜前端架构方案
- **后端项目** → 搜后端架构方案
- **小脚本/工具** → 简单分层即可，不过度设计

### 3. 产出

- `.intentflow/<feature-name>/design.md` — 本次设计文档（必须完成，模板见下）
- `.intentflow/<feature-name>/later-on.md` — 后续想法备忘（模板见下）

## 本次必须完成 — design.md

### 0. 与需求文档的偏差（设计阶段新发现）

需求分析阶段没发现、设计阶段逐一验证时暴露的事实（引用链断了、假设不成立、范围可缩小）。逐条记录，避免执行阶段带着错误假设开工。

- **偏差**：[发现什么] — **影响**：[设计如何调整]

### 1. 模块清单

- **[模块名]**：[层级] — 职责：[职责] — 依赖：[依赖关系]

### 2. 最小依赖链

从入口到数据层跑通本次需求的关键路径和接口：

[高层] → [中间层] → [低层]

同时做跨层依赖体检：逐层确认无反向依赖（下层不依赖上层）。已有结构中的跨层依赖在此标明，列入本次一并修复。

### 3. 测试策略

- **验证方式**：每个模块标注如何验证 — 理由：[肉眼/类型可验证 / 需运行时行为验证]
- **依赖注入点**：需要注入依赖的模块列出注入点（[构造器/参数] 注入 [依赖]，不在内部创建）
- **验证命令**：[验证项]：[命令] — 预期：[结果]
- **Mock 边界**：只 mock 系统边界（外部服务、IO），不 mock 内部协作者

### 4. 决策记录

只记录值得记录的决策，不值得记录的直接实施，不写进文档。判定标准——至少占一条就值得记录：

- **难逆转**：改起来伤筋动骨
- **无上下文难理解**：后来者看到会问"为什么这么干"
- **有真实权衡**：选 A 必然放弃 B

每条格式：

- **决策**：[做了什么选择]
- **理由**：[为什么选它；对比过的备选项与取舍]
- **影响**：[对后续模块/编码的约束，若有]

模块归属与拆分理由属于决策记录范畴，在对应决策条中说明。

### 5. 改动点清单（已有项目）

- 改动点清单 + 新增文件清单（无新增写"无"）
