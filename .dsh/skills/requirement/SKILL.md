# 需求分析

以下规则具有最高优先级。

需求分析是一个迭代收敛过程。
退出条件：需求清晰且可执行。不满足则继续下一轮。

---

## 核心循环

每轮从第 1 项开始，按需执行 2-4 项。不要求每轮全部执行，不要求固定顺序。

### 1. 信息收集与澄清

提问密度由信息缺口决定：
- 缺口大 → 多维度并行问
- 接近清晰 → 收尾问题

覆盖维度：
- 核心目标 = {解决谁的什么问题}
- 核心功能 = 至多 3 个
- 业务规则 = {计算逻辑、约束条件}
- 实现对齐 = {每个需求必须能落到一条具体的实现路径上——以什么方式、经由什么环节实现；未对齐时先检查推导深度，再归因需求}

约束推导：以已确认的实现路径为锚点，agent 基于已知环境约束（file://、无后端、单文件等）自行推导技术约束，以"假设-确认"形式呈现给用户确认/纠正，不向用户开放提问技术权衡。

> 基于 {约束}，数据需以 {方式} 处理，对吗？

用户只回答：业务行为、意图、边界场景的期望表现。答不上来的细节 → 标记延后，不追问到底。

越界规则：只追约束（什么必须成立），不追选择（哪个方案更好）。方案比较类问题（localStorage vs 内存、单模板 vs 独立文件）不追问、不问用户，记录为 design 阶段决策。

停止标准（三态收口）：实现路径上每个环节必须标注三态之一，不允许"未检查"态：
- ✅ 明确：约束已推导并经用户确认，且有对应测试点
- ⏸ 延后：标记触发条件——什么情况下才需要回答
- 🎯 design 决策：方案比较类问题，记录问题本身，交由 design 选择

自检：design 拿到文档开工时会不会回头问需求？会 → 继续推导，未收口。

每轮结束时标记已确认清单 + 仍模糊清单。

### 2. 联网搜索（按需）

**触发**：主动判断以下场景，不询问用户"要不要搜"：

- 共性问题（有成熟方案）→ 搜别人怎么解决的、最佳实践
- creative → 搜同类项目做了什么、解决了什么
- 模糊概念 / 找灵感 → 扩大范围搜行为相似但不同领域的启发内容
- 任何上述场景 → 顺带搜踩坑记录和解决方案

### 3. 预设测试

根据当前理解，从用户视角写一个可执行的测试步骤：

> 操作：{用户做什么} → 预期结果：{系统应响应什么}

- 写得出来 → 需求已具备可执行性，测试方案作为交付物
- 写不出来 → 需求不够具体，回到第 1 项继续收集

与实现对齐联动：实现路径上的每个明确环节都应至少对应一个测试点。推导出的约束转化不成测试点 → 推导未到底。

### 4. 收束边界

每轮判断时间窗口：
- **此时必做**：缺少就转不动的
- **此时不做**：标记延后理由 + 什么条件下才需要做

不做"永远不做"的判断，只判断"此时"。

---

## 退出条件

同时满足 5 项才算清晰且可执行：

1. 核心目标无歧义，一句话可概括
2. 核心功能可列出（≤3 个），规则清晰
3. 至少一个预设测试方案可写可执行
4. 每个核心功能都能落到具体实现路径，路径上每个环节已三态收口（明确/延后/design决策）
5. 必做/延后边界已划定

不满足 → 继续下一轮。
满足后输出需求文档。

---

## 创建 Feature 目录

**命名规则**：以业务对象命名。

- ❌ 以手段命名：`repair-with-template-method`、`migrate-by-batch`
- ✅ 以对象命名：`tool-repair`、`database-migration`

生成 kebab-case 短名 → 展示确认。

确认后创建 `.intentflow/<feature-name>/` 目录。

---

## 交付物

保存为 `.intentflow/<feature-name>/requirement.md`，按以下格式输出：

```markdown
# 需求文档：[功能名称]

## 项目意图
[一句话描述核心目标]

## 功能清单
1. **[功能1]**：[一句话描述]
（列出所有识别到的功能，不做核心/非核心区分）

## 核心功能

### 核心功能1：[功能名称]
- **能力**：系统能够 + [动词] + [业务对象] + [关键约束]
- **业务价值**：[直接产生的业务成果]

### 核心功能2：[功能名称]
（最多 3 个，超出标记为扩展）

## 业务规则

### [规则名称]
- **场景**：[什么情况下触发]
- **行为**：[系统如何响应]
- **异常处理**：[异常情况怎么处理]

## 预设测试

> 从用户视角可执行的测试步骤，验证功能是否符合预期。

### 前置条件
[验证前需要准备什么：数据、环境、账号等]

### 测试步骤

1. **[操作]**：[用户做什么]
   **预期结果**：[系统应该出现什么]

### 异常场景

- **[异常情况]**：[操作] → [预期处理方式]

## 边界收束

**此时必做**：
- [缺少就转不动的]

**此时不做**：
- [延后项] — [延后理由 + 什么条件下才需要做]

## 实现对齐

每个需求必须能落到一条具体的实现路径上——以什么方式、经由什么环节实现。未对齐时先检查推导深度，再归因需求。

锚定实现路径前，先读 `.intentflow/_packages/` 下对应的模块 yml 作为现状基线（模块职责/入口/依赖），不重新扫目录。发现 yml 与代码现状不符时，先校准 yml 再继续。

- **[功能]**：[实现路径：以什么方式、经由什么环节实现，一句话]
- **推导出的约束**：[agent 基于环境约束自行推导、经用户确认的技术约束]
- **design 决策**：[方案比较类问题（A vs B），记录问题本身，交由 design 阶段选择]

与预设测试的关系：实现路径上每个明确环节都应在预设测试或异常场景中找到对应测试点。
```
