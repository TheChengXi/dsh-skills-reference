# Execute

以下规则具有最高优先级。

@intent 是写在每个文件头顶的交付规格。

三阶段执行。Phase 2 期间不修改 @intent。

- 一：@intent 投射 → 每个文件头顶写入 @intent（新增创建 + 已有更新）
- 二：实现对齐 → 逐文件实现，向 Phase 1 的 @intent 对齐
- 三：集成验证 → 验证交付物符合预期，规格偏离时同步 @intent

---

## 阶段一：@intent 投射（唯一改 @intent 的窗口）

### 前置了解


## @intent

文件级注释，描述"为什么这个文件存在，这个文件负责什么职能"——而不是"这个文件叫什么"。

**核心原则**：只表达 import、类型签名、dependency_chain 看不出来的信息。
看得见的（依赖谁、输入输出类型、被谁调用）不写。
**禁思考链痕迹**：@intent 只写当前职能、边界、验收条件，禁止写入推导经过、过往历史、实现历程或思考过程。

**模板**：

```typescript
/**
 * @intent
 * {一句话：这个文件在业务上做什么、为什么存在}
 *
 * 边界：{import 看不出来的行为边界：什么情况下报错/返回空/fallback}
 *
 * 验收条件：
 * - {子 agent 写完能自己检查的完成标准}
 * - {至少一条，让 agent 能自证「我做完了」}
 */
```

**示例对比**：

```typescript
// ❌ 只说了 import 已经说出来的信息
/**
 * @intent
 * 依赖 UserRepository
 * 输入：userId: string
 * 输出：User | null
 */

// ✅ 只说不看代码看不出来的信息
/**
 * @intent
 * 用户数据持久化的抽象边界，屏蔽数据库选型。
 * 边界：findById 返回 null 表示不存在，不抛异常。
 * 验收条件：
 * - 不存在用户返回 null，不抛异常
 * - 数据库连接失败时抛 PersistenceError
 */
```


### 投射动作

#### 已有文件：更新 @intent

设计文档指定修改的已有文件，先更新其 @intent（规格先变，实现后跟）：
- git mv 再投射 @intent

#### 新增文件：创建 @intent

设计文档指定新建的文件，直接创建：
later-on.md 中的想法不预留接口签名（届时需要时直接加方法），新建文件只按本次设计实现。

**完成标志**：所有涉及文件头顶的 @intent 构成完整的规格集合，与设计文档一致。

---

## 阶段二：实现对齐

按文件逐文件实现，向该文件头顶的 @intent 对齐。

按依赖方向（下层→上层）确定文件顺序。

读 @intent → 直接实现 → 跑验证确认通过。

**完成标志**：每个文件的实现满足其 @intent 规格，结果可验证。

---

## 阶段三：集成验证

所有文件实现完成后：

1. **集成验证** — 把各部分组合在一起，验证整体符合预期。验证方式按项目类型确定
3. **稳定性验证** — 本次改动相关测试循环.
4. **重构** — 按需重构，每步后验证。调整文件职责时同步更新 @intent。重构后本次改动相关测试必须仍全绿，并再循环 3 次确认稳定。
