# 令我满意的 skill — Skill 质量标准

本文档定义 Skill 书写的质量标准。它是参考而非工作流——不定义"怎么做"，只定义"什么算好"。
其他 Skill 或系统提示可通过 `参见 skill-standards-ref` 引用此标准。

---

## 0. 前置默认

规则在声明后即具有最高优先级，覆盖模型默认行为。

```
以下规则具有最高优先级。
```

---

## 1. 去人称化

删除"你"、"你的"、"用户"等词语，直接描述操作对象和规则。

对比类别：角色化叙说（❌）→ 过程声明（✅）

❌ 你需要先读取需求文档
✅ 先读取需求文档

❌ 询问用户是否需要搜索
✅ 触发联网搜索确认

❌ 你的角色是资深程序员
✅ 角色：资深程序员

❌ 等用户确认后再执行
✅ 确认后执行

❌ 你不确定某个模块的入口
✅ 模块存在多个未知入口

❌ 告知用户设计完成
✅ 通知设计完成

---

## 2. 过程式声明

用条件、动作、边界定义行为，像定义函数一样。

模板：

```
当 {条件} → {动作} → {完成标志}
```

❌ 如果用户需要检查依赖关系，建议使用 trace_dependency_chain 这个工具来分析
✅ 目标文件超出知识范围 → 调用 trace_dependency_chain

❌ 在修改之前，应该先读一下设计文档，确保你理解了整体架构
✅ 前置读取：.intentflow/<feature-name>/design.md

完成标志必须是可检查的（"全量测试通过"而非"保证代码质量"）。

---

## 3. 极简无歧义

每个词是参数，每句话是指令。删掉不改变模型行为的陈述，以下类型直接删除：

- 论证说服
- 目的解释
- 比喻修辞
- 铺垫
- 弱化词（建议你、可以考虑）
- 「请」

---

## 4. 不角色扮演

书写角度是"模型该以何种内部状态执行"，而非"用户希望模型怎么表现"。

❌ 你应当像一位资深的架构师那样思考
✅ 按以下步骤做架构决策

❌ 请你耐心地引导用户
✅ 每轮最多 2 个问题，等回复后继续

❌ 你是一位友好的客服
✅ 使用以下话术模板

❌ 像一位老师一样解释
✅ 按定义→举例→对比的顺序说明

---

## 5. 不做信息冗余

去掉解释性、教育性、说服性段落——模型需要指令，不是教育。

实例（改前 230 行 → 改后 130 行）：

```
❌ 研究表明，问清楚再动手是最有效的系统级干预...
AI 编程的常见问题是「太主动」—— 自己猜、自己决策...
停下来问 ≠ 效率低。问清楚再做，比做了再改效率高得多。
大问题直接写代码 ≈ 蒙眼走路...

✅ 不确定时不猜测，停下来问。
必须询问的场景：需求理解有歧义 / 技术选型有多个方案 / ...
可以不问的场景：纯技术细节无歧义 / 规范已给出 / ...
提问方式：给出选项 + 分析，不做纯开放提问。
```

---

## 6. 不兜底

只处理确定会发生的路径。不存在的分支不需要防御。

skill 中不写：

```
如果都不满足 → 使用默认策略  // 没人能走到的 else
以防万一，回退到...           // 测试没覆盖的兜底
```

列举判定：

- 列举模型知识库中已有的常识（常见范式、常见方案）→ 预设模型不知道 → 兜底 → 删除
- 列举项目专有/非公开知识（自有术语、自有规则）→ 模型确实不知道 → 锚定 → 保留

---

## 7. 流程描述衔接

当多个 skill 属于同一流程时，description 应设计为**独立可读、列表连贯**。

前提：仅当能同时控制以下两项时有效——

1. description 的内容：自主编写而非自动生成
2. skill 在列表中的排列顺序：框架不重排

原则：

- **独立可读**：每个 description 脱离上下文也能被 LLM 理解
- **列表连贯**：相邻条目的句式结构、动词时态、术语一致
- **减少重复**：上游 description 声明过的上下文，下游不再重复

示例：

```xml
<skill>
  <name>requirement</name>
  <description>在对话中收集需求，生成 feature 名，建立目录并输出需求文档。</description>
</skill>
<skill>
  <name>design</name>
  <description>判断项目状态，路由到修改或新增分支执行结构设计。</description>
</skill>
<skill>
  <name>execute</name>
  <description>向文件投射 @intent 规格，TDD 逐文件对齐实现，集成验证。</description>
</skill>
```

适用范围：功能独立的 skill（搜索、文件操作等单步工具）不适用，仅针对流程型多 skill 编排。

---

## 8. 不用表格、不画图

skill 的 md 不画图、不以表格形式呈现内容。结构化信息直接以文本行输出，XML 式标记可选。

❌ markdown 表格：| 条件 | 动作 | 完成标志 |
✅ 文本行：条件 → 动作 → 完成标志
✅ XML 式标记（可选）：<step condition="..." action="..." done="..."/>

---

## 附带效应：信息下沉

当 SKILL.md 过长时（即使每行都是有效指令），应将参考性内容（输出格式、术语表、检查清单）外链到独立文件，SKILL.md 只保留步骤和完成标志。

```
// 推荐结构
SKILL.md               → 步骤 + 完成标志 + 上下文指针
OUTPUT-FORMAT.md       → 输出模板（参考）
GLOSSARY.md            → 术语定义（参考）
include/CHECKLIST.md   → 检查清单（参考）
```

---

## 9. 禁止思考链残余

文档写最终产物，不写推导过程。思考链（内部中间推理步骤）只在作者脑中完成，不落入文档。

### 识别

一句话属于「中间推理」或「最终结论」——前者删，后者留。

```
❌ 由于模块间存在耦合，考虑到需保持一致，因此先定义接口再实现
✅ 模块间存在耦合 → 先定义接口，后实现

❌ 我们尝试了 A 与 B，发现 B 更稳定，于是采用 B
✅ 采用 B 方案

❌ 这说明缓存并非总是有效，故取消缓存兜底
✅ 缓存不作为兜底依据
```

### 删句检测

删掉某句后规则、行为、边界不变 → 该句是思考链残余，删除；改变 → 保留。

### 边界

决策理由、推导过程、论证说理、模拟思考段一概不写入；文档只保留规则、示例、完成标志。

---

## 总结

0 前置默认：声明规则优先级
1 去人称化：不用「你」「用户」
2 过程式声明：条件→动作→完成标志
3 极简无歧义：每个词都是参数
4 不角色扮演：不给模型做人设
5 不做冗余：不解释、不论证、不铺垫
6 不兜底：不存在的不防御；常识性列举即兜底
7 流程描述衔接：独立可读、列表连贯
8 不用表格、不画图：结构化信息用文本行
9 禁止思考链残余：文档留结果不留推导，删句不变即残留
