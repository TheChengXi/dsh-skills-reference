# 需求文档：skill 引用插件的写入守卫与 client 类型检查

> 来源：`.intentflow/_backlog.md` 待修缺口 1、2。

## 项目意图

让 dsh-skills-reference 的两处无声失效变得可见且可拦：目标工作区不可用时不再凭空建出 `.dsh` 目录，client 半的类型错误不再逃逸检查。

## 功能清单

1. **目标工作区可用性判定**：宿主对 targetPath 判定「存在且为目录」，结果可被面板获取
2. **写入前置拦截**：判定不可用时拒绝写入，不创建任何目录或文件
3. **不可用态呈现**：面板以错误态呈现不可用原因
4. **不可用禁写**：不可用时编辑与保存操作不可用
5. **可用性恢复重载**：路径变回可用后自动重新载入并恢复编辑态
6. **client 半类型检查命令**：一条可运行命令覆盖 `src/client` 全部文件
7. **类型检查纳入构建**：类型错误使 `npm run build` 失败
8. **react 类型依赖**：以 devDependency 提供 `@types/react`

## 核心功能

### 核心功能1：目标工作区可用性守卫

- **能力**：系统能够在写入引用声明前判定目标工作区「存在且为目录」，不满足时拒绝写入，且不在该路径下创建任何目录或文件
- **业务价值**：手填或误选到不存在/非目录的路径时，不再于该处凭空生成本不属于它的工作区目录树与声明文件

### 核心功能2：不可用态的面板呈现

- **能力**：系统能够在目标工作区不可用时，以错误态呈现原因、禁用写操作，并停止展示基于该路径的声明列表、引用源状态与 skill 预览；路径恢复可用后自动重新载入
- **业务价值**：用户即时看到「路径不可用」，不再把它误读为「该工作区没有声明」

### 核心功能3：client 半类型检查

- **能力**：系统能够以一条可运行命令对 `src/client` 全部文件做 strict 类型检查，并因类型错误使 `npm run build` 失败；react 类型由 devDependency 提供
- **业务价值**：client 半的类型错误从「只靠人工 review」变为「构建期自动拦截」

## 业务规则

### 可用性判定

- **场景**：面板载入、切换、手填目标路径，以及任何一次写入之前
- **行为**：判定 = `stat(targetPath)` 成功且 `isDirectory()` 为真；路径不存在或指向文件 → 不可用
- **异常处理**：判定自身抛错（权限等）同样按不可用处理；判定不可用 → 不写入、不建目录

### 不可用态

- **场景**：目标路径判定为不可用
- **行为**：面板进入错误态并给出不可用原因；编辑区（声明列表、引用源状态、skill 预览）不展示；保存与取消均不可用
- **异常处理**：路径由不可用变为可用（用户改完输入或重新选择）→ 自动重新载入、恢复编辑态，旧错误清除

### 合法空态

- **场景**：目标路径存在且为目录，但 `<target>/.dsh/skill-references.yml` 不存在
- **行为**：这是合法空态而非错误——进入编辑态、声明列表为空（呈现「尚未声明任何引用源」）、保存可用
- **异常处理**：声明文件存在但 YAML 非法 → 维持既有行为，以 `解析声明失败: …` 错误态呈现

### 逐字符即时校验

- **场景**：目标工作区输入框的每次 `onChange`
- **行为**：即时 `setTargetPath` → 载入 → 校验，不可用态随输入实时变化
- **异常处理**：输入中间态（如 `D:\w`）短暂判为不可用属预期，不加防抖、不做特殊豁免

### 空 targetPath

- **场景**：targetPath 为空串或纯空白
- **行为**：维持既有判定，返回 `targetPath 为空`，不写入
- **异常处理**：空串判定先于可用性判定

### client 类型检查

- **场景**：执行 client 类型检查命令，或以 `npm run build` 走完整构建
- **行为**：对 `src/client` 全部文件按 strict 做类型检查，任一错误即命令失败；`npm run build` 的类型检查环节失败即整体构建失败
- **异常处理**：react 及 JSX 运行时类型由 `@types/react` 提供；react 本身仍为构建产物外的运行时依赖

## 预设测试

> 从用户视角可执行的测试步骤，验证功能是否符合预期。

### 前置条件

- 仓库工作副本，依赖安装完成（含新增的 `@types/react`）
- 一个已存在的目标目录（记为 `<target>`，初始不含 `.dsh`）
- 一个不存在的路径（记为 `<missing>`，如 `<tmp>/skill-ref-missing-<时间戳>`）
- DSH Web GUI 已加载本插件，输入框工具行的 `skill` 入口可见

### 测试步骤

1. **打开面板**：点击 `skill` 入口
   **预期结果**：目标工作区默认填入当前会话 cwd，且正常载入（cwd 存在）

2. **手填不存在的路径**：在目标工作区输入框填入 `<missing>`
   **预期结果**：状态条提示目标工作区不可用；编辑区（声明列表、引用源状态、skill 预览）不展示；保存与取消不可用；`<missing>` 下未出现任何目录

3. **手填存在的目录**：把输入改为 `<target>`
   **预期结果**：进入编辑态，声明区显示「尚未声明任何引用源」，无错误提示

4. **添加引用并保存**：添加一条引用源并点击「保存并应用」
   **预期结果**：`<target>/.dsh/skill-references.yml` 生成，内容与面板一致；重新载入后条目一致

5. **改回不存在路径**：把输入改回 `<missing>`
   **预期结果**：立即回到不可用态，第 4 步已保存的内容不落盘到 `<missing>`，且该路径仍未被创建

6. **再改回存在目录**：把输入改回 `<target>`
   **预期结果**：自动重新载入并恢复编辑态，列表内容为第 4 步保存的条目，旧错误清除

7. **用选择目录**：点击「选择目录」并选一个存在目录
   **预期结果**：与手填同路径等价（正常载入）

8. **client 类型检查拦截**：在 `src/client` 故意引入一处类型错误（如给 `useState` 传错类型）后运行 `npm run build`
   **预期结果**：构建失败，并指出该文件与行号

9. **修正后完整构建**：还原类型错误后运行 `npm run build`
   **预期结果**：宿主 `tsc`、client 类型检查、esbuild 三步全部通过，产物 `lib/index.js` 与 `lib/client.js` 正常生成

10. **既有测试**：运行 `npm test`
    **预期结果**：既有测试全绿

### 异常场景

- **targetPath 为空串**：清空输入框 → 提示 `targetPath 为空`，不写入、不建目录
- **targetPath 指向文件而非目录**：手填一个已存在的文件路径 → 判为不可用，不写入
- **目标目录存在但无写权限**：手填该目录并保存 → 不在前置判定覆盖范围内，由既有写入失败通道提示 `写入声明失败: …`
- **目标路径为相对路径或带尾随分隔符**：手填 `.` 或 `<target>/` → 规范化后判定，存在即可用（规范化口径见实现对齐）
- **声明文件 YAML 损坏**：在可用目标下手写坏 `<target>/.dsh/skill-references.yml` 后重新载入 → 呈现 `解析声明失败: …` 错误态

## 边界收束

**此时必做**：

- 宿主侧写入前的可用性判定 —— 不误建目录的根治点
- 面板不可用态：提示 + 禁写 + 不进编辑态
- `src/client` 全覆盖的 strict 类型检查，且并入 `npm run build`
- `@types/react` 作为 devDependency 引入

**此时不做**：

- 「不可读/不可写」的前置权限探测 — 延后理由：Windows 上可靠判定成本高，且既有 `replace` 写入失败通道已能呈现；触发：出现「路径存在但无权限」导致静默失败或误报的实测复现
- backlog 缺口 3（`list` 丢弃 `Observation.complete`）— 本轮不做，转由 design 阶段登记为 later on
- backlog 缺口 4（cwd 规范化与官方不一致）— backlog 自身已要求「等实测复现」，转由 design 阶段登记为 later on
- backlog 演进待办各项（目标工作区输入历史、目录选择失败提示、入口按钮 hero 态与健康角标、面板结构拆分、预览即时性、健康度根因、引用能力扩展）— 触发条件均未成立，转由 design 阶段登记为 later on
- 类型检查的增量/缓存优化 — 延后理由：当前文件规模下全量检查耗时可接受；触发：client 半规模增大导致构建明显变慢

## 实现对齐

- **目标工作区可用性判定**：宿主在 RPC `list` 路径上对 targetPath 做一次「存在且为目录」判定，结果随返回一并回传面板；`writeReferences` 的无条件 `mkdir(dirname(filePath), { recursive: true })` 被前置拦截取代——不可用时根本走不到写。
  - 🎯 design 决策：判定放在哪一层（`references-store` 内前置校验 vs `rpc` 编排层 vs 新增 RPC 方法）；「不可用」在 `list` 返回形状上如何承载（复用既有 `error` 字段 vs 新增状态字段）；`replace` 是否复用同一判定以避免 list 与 replace 口径分叉
- **不可用态**：`controller` 依据判定结果置错误态，面板编辑区与底部按钮由该状态派生——复用既有 `state.error` 与 `phase` 通道。
  - 🎯 design 决策：是否需要独立 phase/字段以区分「不可用」与一般业务错误；`pickDirectory` 选到不可用目录时是否同样进入该态
- **可用性恢复重载**：沿用 `setTargetPath` → `load()` 既有链路，不新增触发点。
  - ✅ 明确：逐字符 `onChange` 即时校验（用户确认），中间态短暂不可用属预期
- **client 半类型检查**：新增覆盖 `src/client` 的 tsconfig 与 npm script，并在 build 流程中前置执行；模块解析策略需与现状（client 半使用无扩展名的相对导入，如 `./controller`、`../contract`）相容。
  - 🎯 design 决策：`moduleResolution: bundler` vs 给 client 半补 `.js` 扩展名；独立 `tsconfig.client.json` vs 主 tsconfig 拆分/引用；script 命名
- **react 类型**：devDependencies 增加 `@types/react`，`build.mjs` 的 `external` 列表与产物格式不变（react 仍由宿主运行时提供、不进 bundle）。
  - 🎯 design 决策：`@types/react` 的具体版本
- **权限类判定（不可读/不可写）**：⏸ 延后——本轮实现路径不含前置权限探测，写入失败仍由既有 `replace` 错误通道呈现；触发条件见「此时不做」首条

**推导出的约束**：

- 判定口径 = 「路径存在且为目录」，不要求含 `.git` 或 `.dsh`（用户确认）
- 不可用 = 整体不可用：提示 + 禁写 + 不进编辑态（用户确认）
- 校验时机 = 逐字符即时（用户确认）
- client 类型检查纳入 `npm run build`，类型错误即构建失败（用户确认）
- 允许新增 devDependency `@types/react`（用户确认）
- client bundle 的运行时依赖仍由宿主提供：`build.mjs` 的 external 列表与 `window.__ModuleLoader__` 产物格式不得因类型检查而改变
- 宿主半与 client 半共享 `src/contract.ts`，两侧类型检查必须都能解析同一份 contract（client 半以无扩展名相对导入引用它）
- `targetPath` 为空串的既有判定（`assertTargetPath` → `targetPath 为空`）保持不变，且先于可用性判定

**与预设测试的关系**：判定口径对应测试 2/3/7 与「指向文件」异常场景；写入拦截对应测试 2/5；不可用态与禁写对应测试 2；恢复重载对应测试 5/6；合法空态对应测试 3/4；空串与 YAML 损坏对应异常场景；client 类型检查对应测试 8/9；react 类型依赖对应前置条件与测试 9。
